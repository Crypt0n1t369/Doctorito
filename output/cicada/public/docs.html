Cicada

A data channel made of sound. One speaker, any number of listening devices, no network, no pairing, no camera. Roughly 122 bytes a second in a band you can hear.

What this is

Cicada modulates arbitrary bytes into audio between 672 and 2313 Hz and demodulates them back on anything with a microphone. The physics buy you three properties that are awkward to get any other way:

  • No pairing. A device that can hear is a device that can receive. There is no discovery, no handshake, no session, no return channel.
  • One to many, for free. One speaker reaches every device in earshot at once. The hundredth listener costs exactly what the first did.
  • Range is the room. Sound stops at the walls. You cannot receive a message you were not physically present for, which makes proximity a property of the medium rather than something you have to prove.

It also travels anywhere audio already travels: a PA system, a phone call, a radio broadcast, a video file, a voicemail.

The band is audible on purpose. Ultrasonic carriers are inaudible to people but not to microphones, which makes them a covert side channel. If a device is transmitting, the people near it can hear that it is.

Quickstart

Render a message to audio:

curl -X POST https://api.cicada.audio/v1/transmissions \
  -H "Authorization: Bearer $CICADA_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text": "Gate 14 · boarding closes 18:40", "profile": "robust"}'

Play the audio_url through any speaker. On the receiving side:

import { listen } from "https://cdn.cicada.audio/cicada.js";

const rx = await listen({
  onMessage: m => console.log(m.channel, m.text),
});
// later: await rx.stop();

Receiving needs no key and costs nothing — it runs entirely in the listener's browser. Only rendering and server-side decoding are metered.

Profiles

A profile fixes the frame size. Larger frames spend proportionally less time on preamble, so they carry more per second — but a frame is all-or-nothing, so a longer one gives a burst of noise more to ruin and offers fewer points at which the receiver can re-acquire.

ProfileFrame1 frame holds ThroughputUse it when
micro16 B11 B~16 B/s Card references and short tokens. Single-frame only.
robust64 B59 B~53 B/s Noisy rooms, moving listeners, anything you cannot repeat.
standard128 B123 B~86 B/s The default. Start here.
fast512 B507 B~146 B/s Quiet, close, controlled paths — a cable, a phone call, a quiet room.

Throughput is payload bytes per second of airtime at one pass, including the 0.30 s gap between bursts. GET /v1/capacity?bytes=N works this out for a specific payload and recommends a profile; it is free and unmetered.

Passes

A broadcast has no acknowledgements, so the only defence against a listener who arrived late or looked away is to send the thing again. repeats controls that. Repeats do not add content — a receiver recognises the second copy and discards it — they add chances.

Channels and signing

A channel is a 16-bit number carried in every frame, so a receiver can ignore traffic that is not addressed to it. Mark a channel signed and Cicada mints an Ed25519 key pair, keeps the private half on the server, and signs every message you send on it.

Receivers pin the public half:

GET /v1/channels/{id}/trust
Authorization: Bearer rk_…          # the channel's receive token

{ "channel": 2, "signed": true,
  "keys": [ { "key_id": 1, "public_key": "41cc…", "algorithm": "ed25519", "retired": false } ] }

The receive token (rk_…) is designed to ship inside a client. It can read the trust bundle and the card bundle, and post receipts. It cannot render, decode, or read anything else. Your secret key never leaves your server.

What a signature does and does not tell you

  • It establishes that the holder of the channel's private key produced these exact bytes.
  • It does not establish that the content is true, current, or that the person who commissioned it was authorised to. Sign the claim; do not confuse it with the fact.
  • It is bound to one channel. The channel number is inside the signed bytes, so the same message relayed onto a different channel does not verify.
  • It does not stop replay on its own channel. A recorded broadcast can be played back later and will still verify. Put a timestamp or a sequence number in your own payload if that matters — Cicada deliberately does not decide your freshness policy for you.

Rotation

POST /v1/channels/{id}/rotate issues a new key id and retires the old one. Retired keys stay in the trust bundle for 90 days, because there is no return channel over which to coordinate a cutover: a receiver that has not synced recently must still be able to verify a transmitter that has not updated recently.

Signing costs 68 bytes on the air (a 64-byte signature plus a 4-byte key id). On a micro frame that leaves nothing, so signed messages need robust or larger.

Cards

Airtime is the scarce resource. Storage is not. A card is a payload you publish once through the API; receivers cache the bundle over their normal network connection, and on the air you broadcast only its four-byte code. 

# Publish the content once
POST /v1/channels/{id}/cards
{ "label": "Platform change", "json": { "train": "IC2041", "from": "4", "to": "11" } }
→ { "code": 1, "bytes": 65, "version": 1 }

# Broadcast four bytes
POST /v1/transmissions
{ "channel": "ch_…", "card": 1, "profile": "micro" }
→ { "body_bytes": 4, "seconds": 0.55 }   # one pass, unsigned
PayloadSent directlyAs a card reference
65 B of JSON1.20 s0.55 s
1 KB6.72 s0.55 s
10 KB68.6 s0.55 s
60 KB6.9 min0.55 s

Airtime per pass, unsigned. On a small payload the saving is unremarkable — the argument is the last three rows: the airtime never grows. Receivers resolve the code locally with no network round trip, so resolution works offline too.

Cards are the right tool when the set of things you might say is known in advance — platform changes, exhibit numbers, menu items, shelter statuses. They are the wrong tool for content that is genuinely novel each time, because the receiver has to have synced it first.

The one cell that fails badly is micro through a broadcast chain. A micro burst is eleven OFDM symbols long; a limiter driven 12 dB into compression flattens the peaks and there is not enough of the burst left to average over. If you are going out over a broadcast or a PA with heavy loudness processing, do not use micro — use robust, and accept the extra 0.3 s.

These are models, not measurements. They are reproducible from a seed and they exercise the real modem, so they are good for comparing profiles against each other. They are not evidence that a particular room behaves this way. Measure anything you intend to deploy.

Browser SDK

import { listen, transmit, decode, encode, downloadWav, CicadaClient } from "/cicada.js";

// Receive from the microphone
const rx = await listen({
  trust: { "2/1": "41cc…" },          // channel/keyId → Ed25519 public key
  cards: { 1: '{"train":"IC2041"}' }, // cached card bundle
  onMessage: m => { /* m.text, m.card, m.verified, m.channel */ },
  onEvent:   e => { /* frame, duplicate, rejected, foreign-frame, error */ },
  onLevel:   l => { /* l.peak, l.rms */ },
});
console.log(rx.stats);   // detected, decoded, undecodable, frames, messages, duplicates
await rx.stop();

// Transmit through the speakers
await transmit({ text: "hello", profile: "robust", repeats: 2 });

// Encode without playing, then save
const { samples } = encode({ json: { gate: 14 }, profile: "standard" });
downloadWav(samples, "gate.wav");

// Decode a file the user picked
const { messages } = await decode(await file.arrayBuffer());

The microphone needs a secure context

Browsers grant microphone access only over https or on http://localhost. A LAN IP address and a file:// page are both refused no matter how many times the user agrees. micAvailability() tells you which case you are in instead of failing silently.

The SDK asks for the microphone with echo cancellation, noise suppression and automatic gain control switched off. Those are tuned for speech and will chew on a modem signal sitting in the same band.

Wire format

Sample rate8 kHz mono
Band671.9 – 2312.5 Hz (FFT bins 43–148)
ModulationOFDM, 106 carriers, differential QPSK with Gray mapping
Symbol512-point FFT + 64-sample cyclic prefix = 72 ms
CodingRate-½ convolutional, K=7, polynomials 0o133/0o171, soft-decision Viterbi
InterleaverDeterministic coprime stride over the whole codeword
IntegrityCRC32C over the frame; a burst that fails it is discarded, never guessed
Preamble128 ms linear chirp, 700→2300 Hz, found by matched filter

Framing

A message that fits one frame uses a 5-byte header; longer ones use 12 bytes.

solo    ver:u8 | flags:u8 | channel:u16 | len:u8
multi   ver:u8 | flags:u8 | channel:u16 | messageId:u32 | offset:u16 | totalLen:u16

flags   bit0 signed   bit1 solo   bit2 card reference

signed message body:   keyId:u32 || payload || ed25519sig:64
card reference body:   code:u32

signature covers:      channel:u16 || keyId:u32 || payload

The channel number is inside the signed bytes but is not repeated in the body — it already travels in every frame header, so binding it costs nothing on the air. Without that binding a signature would be valid for its bytes on any channel, and a relay onto a different one would be stopped only by the trust table happening to hold a different key there.

There is no CRC in the frame header because the modem has already checked CRC32C over the whole burst — a frame that reaches the framing layer is intact.

What is actually measured

These numbers come from running the real modem, and you can reproduce them with npm run bench:

122 B/s128-byte frames, burst only
163 B/s512-byte frames, burst only
−4 dB SNR128-byte frames still decode 97 of 100 times in additive white noise
−3 dB SNR512-byte frames, 98 of 100 — then a hard cliff by −4 dB

Decoding at negative SNR means the modem works when the noise is louder than the signal. That is what the coding and the coherent OFDM gain buy you, and it is why the audible band is usable at a polite volume.

Every figure above is from software: synthetic channels, no physical speaker, room or microphone anywhere in the measurement. They bound what the modem can do, not what your deployment will do.

Where this fails

  • Long reverberation. The cyclic prefix is 8 ms. A room whose echoes run much longer than that smears one symbol into the next, and no amount of volume fixes it. Reverberant halls, atriums and stairwells are the hard case — not distance.
  • Aggressive loudness processing. OFDM has a high peak-to-average ratio, so a broadcast limiter pushed hard flattens exactly the peaks that carry the information. The broadcastFm simulation exists because this is the most common real-world killer.
  • Voice-tuned audio processing. Noise suppression and automatic gain control are designed to remove things that are not speech. A modem in the speech band looks exactly like something to remove. Turn them off on capture; you often cannot turn them off in somebody else's conference system.
  • No acknowledgements. There is no return channel. You cannot know a specific device received something unless it tells you over a network — which is what receipts are, and receipts are only as complete as the devices that chose to send them.
  • Replay. A recording of a valid signed broadcast stays valid. If freshness matters, carry it in your payload.
  • It is audible. That is the design, but it means you cannot use it continuously in a quiet space without annoying people. Send in bursts.

None of this is a reason not to use it. It is the shape of the envelope: short, repeated, authenticated bursts in ordinary rooms, where the alternative is asking someone to install an app, join a network, or point a camera at a sticker.
